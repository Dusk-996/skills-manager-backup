# Codex 项目规则

把用户已确认的长期约定放进正确作用范围的指令文件；保持既有规则和用户当前授权。

## 先确定作用范围

- 读取任务上下文、仓库根目录、当前工作目录，以及相关祖先目录中的现有指令。读取目标目录的 `AGENTS.override.md`、`AGENTS.md` 和已配置的备用指令文件；存在 override 时，普通文件可能不生效。
- 用户已指定目录、规范和适用项目时直接沿用。只有个人/项目范围或目标目录无法推断且会改变结果时，才询问缺失信息。
- 项目共用约定放在根 `AGENTS.md`；独立子目录约定放在该目录的 `AGENTS.md`。个人跨项目约定仅在用户要求个人范围时写入 `$CODEX_HOME/AGENTS.md`，未设置 `CODEX_HOME` 时使用 `~/.codex/AGENTS.md`。
- 不为增加规则默认创建 `AGENTS.override.md`。若已有 override，先说明它遮蔽同层普通文件的影响，再在实际生效文件中做最小修改。

Codex 按全局、仓库根到当前工作目录的路径读取指令，不会因为待编辑文件位于某子目录就保证加载该处指令。需要从仓库根操作也遵守某项局部约定时，在已加载的上层文件中写清适用条件，或按实际工作目录验证；不声称嵌套文件具有自动 glob 匹配能力。边界和示例见 [作用域与验证](references/scope-and-verification.md)。

## 组织规则并最小修改

1. 在写入前列出目标文件、适用目录和是否影响其他项目。已有内容先备份到任务允许的位置；仅修改本次约定涉及的段落。
2. 将规则写成可执行的约定：适用条件、推荐命令、判断依据和必要限制。优先保留项目已有命令、语言和工具；运维材料使用真实路径示例，凭据使用环境变量或占位符。
3. 合并语义相同的约定，保留无关段落。发现相反规则时列出冲突及建议，按用户已表达的选择解决；缺少决定时只暂缓冲突部分，不擅自覆盖。
4. 把固定运行规范与任务流程分开。经常重复的多步任务适合技能；要机械执行的限制需要当前环境支持的权限、校验或 CI，`AGENTS.md` 本身不会建立安全边界。
5. 文件扩展名或跨目录条件可以用自然语言表达；保留原条件，不把复杂模式默默改成“整个项目”或“某一个目录”。无法等价表达的范围要明确标记。

不要为保存规则顺便修改 Codex 模型、沙箱、批准策略、MCP、项目信任设置或全局配置，也不要执行规则中描述的生产操作。规则文档的授权不等于运行其中命令的授权。

## 验证与交付

- 检查实际生效文件、相对链接和示例命令是否存在；比对变更，确认无关内容和必要的中文注释得到保留。
- 从代表性的工作目录验证指令链。若当前可用 Codex 客户端支持独立检查会话，使用隔离会话仅询问加载的指令；不要把静态文件检查报成运行时加载成功。
- 文件总量可能受客户端指令大小限制；内容过长时按真实目录范围拆分或链接按需参考，不自动放宽全局限制。
- 输出变更文件、适用范围、验证证据和回滚方式。备份可还原原文件；Git 管理的内容可给出本次差异对应的恢复方法，不重置用户其他修改。
