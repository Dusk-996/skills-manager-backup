# 作用域与验证

## 目标选择

| 用户意图 | 目标 | 注意事项 |
|---|---|---|
| 全部项目的个人偏好 | `$CODEX_HOME/AGENTS.md`；默认 `~/.codex/AGENTS.md` | 仅在用户要求个人范围时修改；先看全局 override |
| 当前项目统一约定 | 仓库根 `AGENTS.md` | 保留项目现有段落和其他团队约定 |
| 只用于一个服务目录 | 该服务目录 `AGENTS.md` | 验证从该目录启动的指令链；根目录会话不保证自动读取它 |
| 文件类型跨多个目录 | 已生效的项目指令中写明确条件 | 不发明 `globs`、`alwaysApply` 等 Codex 指令元数据 |
| 一次性任务限制 | 当前任务上下文 | 不强行持久化为全局规则 |
| 可复用的部署或排障流程 | 技能 | 使用已有 `skill-creator`，而不是继续增大常驻指令 |

在每个层级，Codex 优先选择非空的 `AGENTS.override.md`，其次是 `AGENTS.md`，再按配置检查备用名称；不是把同层所有文件都合并。根到当前工作目录的更具体指令可覆盖更宽范围的冲突项。系统、开发者与当前用户指令的优先级仍然适用。

## Shell 规则示例

用户要求“整个仓库的 Shell 脚本修改后做语法检查，部署目录还要写回滚步骤”，已有根文件时可只合并这两段：

```markdown
## Shell 脚本

- 修改 Shell 脚本后，对本次改动的脚本执行 `bash -n`；只有环境安装了 ShellCheck 时才追加相应检查。
- 涉及 `deployment/` 中部署脚本时，在交付说明中给出备份、验证与回滚步骤；不要以文档要求替代真实部署授权。
```

这里的路径条件是给代理阅读的约定，不是文件匹配器或强制访问控制。

## 验证样例

在隔离样例树中保留根规则与 `services/api/AGENTS.md`。从根检查应看到根指令；从 `services/api` 检查应看到祖先和更具体指令。若该目录同时有 `AGENTS.override.md`，确认普通文件被遮蔽，而不是声称它也生效。

若当前 Codex CLI 帮助确认支持 `--cd`，可以在新检查会话中仅询问“列出本次已加载的指令文件与适用范围”，分别使用根目录和服务目录作为工作目录。该检查需要实际模型调用；遵守当前工具、网络和权限约束。不能实际启动时，只报告已完成的静态检查及尚未验证的加载行为。

检查清单：目标层级正确、原文件备份可用、冲突已解决、无无关段落丢失、没有把目录条件扩大为全局、没有夹带生产命令执行或配置变更。
