# 映射与冲突

## 持久规则

全项目约定适合根 `AGENTS.md`；真正独立目录约定适合该目录的指令。不要把“所有 Shell 文件”简单迁到某个 `scripts/AGENTS.md`：原文件可能分布于多个目录，且 Codex 的指令发现取决于工作目录路径。

对 `**/*.sh` 等跨目录条件，可以在已生效的根指令中写明“修改本仓库任意 Shell 脚本时……”。这保留阅读条件，不建立自动匹配器。复杂排除条件如“所有 Shell 文件但排除 vendor/ 和第三方包”应完整保留并在报告中说明是自然语言条件。若无法清晰表达，先报告待确认项，不选一个方便的子目录代替。

存在 `AGENTS.override.md` 时，同层普通文件可能被遮蔽。迁移前识别真正生效目标；不要创建一个不会生效的文件后宣称完成。

## 显式命令

假设原命令只在用户明确请求“审查 Compose 变更”时使用。目标技能可以包含以下元数据：

```yaml
---
name: review-compose-change
description: 审查用户指定的 Docker Compose 变更，检查镜像版本、端口、挂载、健康检查和回滚条件；用户明确要求该专项审查时使用。
---
```

其 `agents/openai.yaml` 可写：

```yaml
interface:
  display_name: "Compose 变更审查"
  short_description: "检查指定 Compose 变更的运行约束、配置风险和回滚条件"
  default_prompt: "使用 $review-compose-change 审查本次 Compose 变更，先给出发现和证据。"
policy:
  allow_implicit_invocation: false
```

只有原材料或用户明确要求仅显式调用时才设置上述 `false`。原字段叫 `disable-model-invocation` 也必须先读它的含义；不要在 Codex 顶层元数据中照抄它。普通可复用工作流省略 policy 即可保持默认发现。

## 同名与资源

- 目标技能名称相同、内容相同：保留一份，记录复用，不创建数字后缀副本。
- 名称相同、职责不同：列出职责冲突及建议名称，已有意图不足时再询问；不得覆盖原入口。
- 原脚本引用兄弟资源：复制允许迁移的必要资源，并验证更新后的相对路径。绝对机器路径应改为参数或已明确的目标目录，不能虚构不存在的默认位置。
- 相反规则：在迁移报告中标出对应原文位置和目标段落，先执行用户已有明确选择；未解决的冲突只阻塞该条迁移。
- 外部安装或在线工具依赖：记录前提，不能把一个技能包声称成包含整个运行时或凭据的备份。

## 隔离验收建议

建立仅含演示文档的临时项目：一份项目规范、一份显式任务命令、一份同名不同职责目标。验证前两份映射到不同目标、显式策略正确、同名冲突得到记录且原件摘要不变。再加入跨目录文件条件，确认没有把范围缩为单个目录。

测试目录仅用于迁移样例；不要借验收运行真实部署命令、连接远端服务器或修改当前用户的 Codex 配置。
